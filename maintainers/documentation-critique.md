# Firehose documentation critique

Firehose’s documentation has a sound foundation: readable prose, concrete prompts, consistent navigation, and examples with checkable results. The larger weakness is context. A reader who already understands Firehose can follow the instructions; someone discovering the product must supply too much background. The design has a similar imbalance: it presents articles cleanly, but does little to establish the product, prioritize the first action, or make unfamiliar workflows recognizable. The next iteration should improve orientation and confidence before expanding the page count.

This assessment comes from reading the current guides and inspecting the rendered site at desktop and mobile widths. I also inspected Stripe, Linear, Tailwind, and Vercel’s current documentation. It is an editorial and visual review, not a usability study with independent participants. The existing automated checks provide useful evidence about rendering, links, and accessibility, but they cannot tell us whether a newcomer understands which machine needs configuration or why an agent is waiting.

The most serious gap is the starting boundary. “Connect to Firehose” assumes an existing server and configured provider, then sends newcomers back to whoever supplied their setup. That is honest, but it leaves a public documentation reader without a complete path forward. Add two explicit routes: “Someone set up Firehose for me” and “I’m setting up Firehose myself.” Each needs an access checklist and a clear and verified next step. Until installation is verified, label the supported starting point prominently on the homepage.

Explain the product’s basic arrangement before introducing connection details. A compact diagram should show the reader’s browser, the machine running Firehose, the repository on that machine, and the selected agent provider. Accompany it with three sentences explaining where files live, where commands run, and which machine must stay available. This would answer questions currently scattered across connection, settings, and mobile guides. Define “provider” beside the first selection step, rather than expecting readers to visit the glossary beforehand.

The quickstart also makes readers do substantial preparation before they experience Firehose. Creating a folder, writing JavaScript, initializing Git, making a commit, and configuring project directories are reasonable tutorial tasks, but together they obscure the promised first session. Split the guide into an existing-project route and an optional practice-project route. Keep the greeting example because its results are easy to verify. Add a complete downloadable starter once distribution is agreed, and measure completion time before claiming the guide takes five minutes.

Several instructions describe a decision without teaching readers how to make it. “Review the session’s autonomy settings” is the clearest example. Explain each verified permission option, when it requests approval, and a suitable starting choice for a first task. Similarly, distinguish a provider’s availability from its installation, authentication, and model access. Provide a compact prerequisites table per supported provider. Avoid recommendations about prices, model quality, or permission behavior until they have been checked against the supported release.

The session lifecycle needs its own explanation. Readers need to distinguish working, waiting for input, queued messages, interrupted turns, disconnected views, and completed responses using the actual indicators they see. Build an illustrated state guide after validating those indicators in the product. For each state, explain what it means, what the reader should do, and what action might be premature. Clarify separately what happens when a browser closes, the server sleeps, or a session is restored; those behaviors should never be inferred.

Tool coverage should be organized around decisions and consequences. The Questions guide already explains submission targets and deletion particularly well. Smart Review needs comparable detail about starting a review, acting on findings, and whether an action sends instructions or merely changes a label. Diff needs to explain the comparison base before “cumulative” becomes useful. Add an annotated example showing a changed line, the selected comparison, and the follow-up it motivates. Verify missing behavior rather than filling these gaps with plausible descriptions.

Troubleshooting currently repeats advice such as checking connectivity or reading an error without always providing the diagnostic action. Replace each broad instruction with a small decision path: symptom, check, expected observation, next action. Explain where to find version information before asking readers to include it in reports. Separate problems users can fix from problems requiring the server operator. A good test is whether someone can complete the suggested check without searching another guide for its prerequisites.

The end of a task also needs more context. “Continue your project’s normal review process” assumes a process that first-time users may not have. Add a verified handoff guide explaining how to inspect outstanding changes, decide whether more work is needed, and move into the project’s commit or pull-request workflow. Distinguish ending an agent turn from accepting a change. Show what remains on disk after interruption, and explain cleanup only after confirming the actual controls and their consequences.

The design references deserve a qualified introduction. There is no authoritative ranking of the best-looking documentation. A [developer discussion](https://www.reddit.com/r/reactjs/comments/1dov15v/) praises Stripe and Tailwind while also disagreeing about whether visual restraint counts as impressive. That is useful reputation evidence, not a representative survey. I selected Linear and Vercel as additional visual benchmarks after inspecting their current sites. Their transferable strengths are deliberate hierarchy, recognizable components, and clear starting actions; Firehose should adapt those principles to its smaller scope.

[Stripe](https://docs.stripe.com/get-started) combines a strong introductory heading, task-oriented cards, a restrained accent color, and an illustrative product panel. Its page makes several starting routes visible without reducing everything to a directory. Firehose can borrow that structure: explain the product, present the primary starting route, and offer a few alternatives with one-sentence outcomes. Stripe also places Markdown and agent-oriented actions near the article heading. Our text exports already exist, so a quiet “Read as Markdown” link could improve discovery without introducing another service.

[Linear](https://linear.app/docs) demonstrates consistent spacing, restrained borders, clear grouping, and recognizable icons within a dark interface. Its popular-topic cards create destinations that are easier to distinguish than a uniform list of links. Firehose would benefit from similarly consistent card anatomy, but should avoid copying oversized empty icon areas into a much smaller documentation set. Three compact cards for starting a session, reviewing work, and getting unstuck would provide enough structure. Preserve Firehose’s warmer palette and support both themes equally.

[Tailwind](https://tailwindcss.com/docs/styling-with-utility-classes) places rendered examples beside the code that produces them. That connection makes the documentation visually interesting while helping readers understand cause and effect. Firehose’s equivalent should be a real prompt paired with an annotated result or interface capture. Add this treatment to the first-session, Questions, and Diff guides. Use consistent screenshot framing, captions, and selective callouts. Keep the written explanation complete, and capture the actual product rather than inventing a cleaner interface that readers cannot find.

[Vercel](https://vercel.com/docs) gives its landing page a more pronounced starting area, visible action buttons, and examples close to the introduction. Firehose’s homepage currently reads like another article, including a right-hand contents list that adds little to a short introduction. Give the homepage a distinct layout, remove that redundant contents column there, and create one primary “Start your first session” action. Put connection prerequisites immediately beside it. Keep the normal article layout for procedures, where the contents list helps readers move through longer material.

Typography should become more disciplined without sacrificing readability. The current large headings, generous line spacing, and repeated vertical gaps can make short guides feel longer, especially on phones. Prototype a body size of 17–18 pixels, line height around 1.65–1.75, and prose widths near 65–75 characters. Use a smaller, consistent section-heading scale and tighter spacing within a procedure. These are starting values to evaluate, not universal rules. Preserve visible focus, readable contrast, and comfortable touch targets while adjusting density.

Navigation should reflect reader intent more directly. “Tools,” “Guides,” and “What you can do” overlap, so users must predict our classification before choosing a page. Test a simpler grouping: “Start,” “Work with agents,” “Review results,” and “Reference and help.” Keep exact product labels within page titles and instructions. On mobile, make the menu’s purpose apparent and ensure the active section remains easy to locate. Retain semantic tables for comparisons, but consider stacked summaries for the four-column tool overview.

Introduce a small set of reusable instructional components: prerequisites, numbered steps, expected result, and recovery guidance. Differentiate them through headings, spacing, and modest borders, with color serving as reinforcement. Use notices sparingly so real constraints stand out. The warm orange accent can identify links and primary actions, while neutral surfaces carry most content. Continue using system fonts unless a distinctive typeface proves worthwhile. Consistency in these components will contribute more than decorative gradients, animated backgrounds, or an elaborate custom theme.

Implement improvements in three reviewable passes. First, repair onboarding context, provider prerequisites, and the session-state explanation. Second, redesign the homepage and establish the typography and component rules. Third, add verified captures and refine navigation through observed use. Ask new readers to connect, start a session, answer a question, and inspect a change without coaching. Record hesitation, wrong turns, and completion, alongside accessibility checks. Keep publishing and licensing deferred. Success means readers understand their next action and can recognize when it worked.

# Firehose documentation critique

The documentation’s main weakness is incomplete decision support. Its friendly prose and checkable examples are useful, but readers need clearer explanations of where work happens, what launch settings authorize, and which review controls actually dispatch work. Checking Firehose’s implementation also corrects my earlier assessment: the quickstart already supports an existing repository and links a downloadable example; Firehose already creates Git projects; and its activity model does not contain every state I proposed illustrating. These corrections change both the priorities and the recommended examples.

This revision checks the local `main` checkout at `c57391d84f8d5bd198354fecf9c93c7e85418ec3`, alongside the documentation and earlier desktop/mobile inspection. The [source audit](critique-source-audit.md) records implementation paths, symbols, corrections, and outstanding validation. I traced relevant controls into handlers and inspected existing tests; I did not run Firehose, install a release, or execute its tests. Source evidence establishes implemented behavior, while screenshots, deployment compatibility, and newcomer comprehension still need separate checks. Design observations remain editorial judgments, not measured usability findings or proof of a universally superior layout.

The onboarding boundary needs sharpening, but the earlier recommendation to add two equally complete installation routes was premature. `install.sh` explicitly requires repository and package access through a GitHub token. Public documentation does not establish public product distribution. In `connect.md`, retain the existing direct-server and hosted-app routes, add a short access checklist, and identify who supplies each prerequisite. Keep independent installation in the backlog until an eligible operator completes a clean setup. The acceptance test is whether a newcomer can identify their route and missing access without guessing.

The connection guide already says that repositories and agent processes live on the server. The gap is prominence and reinforcement, rather than an absent explanation. Put that arrangement on the homepage and beside the first project choice: browser → Firehose server → repository and agent runtime. Explain the provider as the selected agent system without suggesting every provider has identical hosting or authentication. Carry the same machine labels into terminal examples. A reader should know exactly where to save `greeting.mjs`, configure project directories, and run its check.

Make the existing-project shortcut an explicit jump to session creation. For a new project, document **Pick a project → New git project → Location → Create** after a product walkthrough. The server creates a repository and README and attempts an initial commit; a failed commit leaves the repository available, with a Git-identity hint in the client. This removes unnecessary manual initialization from that route, but does not create the greeting sample. Keep the existing download and explain how to save it on the server. A bundled starter is optional polish, not missing core functionality.

Launch permissions deserve the highest content priority. The wizard initializes autonomy as enabled. Claude labels its checkbox **--dangerously-skip-permissions**; Codex uses **Full Auto**. The Codex adapter maps enabled autonomy to no approval requests and unrestricted sandbox access; disabled autonomy requests the provider’s approval behavior with workspace restrictions. Antigravity separately exposes editing modes and terminal sandbox controls. Replace “review the session’s autonomy settings” with provider-specific explanations beside the launch step. Document what disabling changes, but do not promise every command then requires approval. Validate each documented provider’s actual approval interaction before recommending a beginner preset.

Provider troubleshooting should also follow actual launch conditions. The footer waits for the selected provider’s models and disables starting when its selected model is unavailable; another provider’s slow discovery should not block it. Add separate cases for **Loading models**, an unavailable selection, and a launch error. Each needs the visible symptom, a check the reader can perform, and an operator escalation when necessary. Build prerequisite entries only for providers whose installation and authentication were verified. A registry entry proves integration exists, not that a particular user has model access.

Replace the proposed universal state chart with a guide to observable signals. Firehose’s turn type is `idle`, `working`, or `stopping`; the sidebar additionally handles closing and unavailable transcripts. Queueing, connection health, and Questions are separate concerns. The current chat guide correctly says a finished turn does not prove task success, but “wait for the interrupted state” needs a more recognizable observation. Describe **Stopping...**, **Idle**, activity, and delivery notices using captures. Keep browser closure, machine sleep, and session restoration as explicit walkthrough cases rather than inferring durability from the state type.

Smart Review has a more specific omission than my original critique identified. **Fix**, **Explain**, **Refine**, **Rewrite**, **Issue**, and **Won’t fix** record triage choices. A separate **Act** control dispatches eligible work; its menu distinguishes **Act on items** from **Clear context and act**. The server closes pending Won’t fix items during that action without sending them to an agent. Expand `tools/smart-review.md` into a choose–dispatch–verify procedure, explaining the selected session and context choice. Demonstrate one finding from selection through dispatch and rechecking, so readers do not mistake a highlighted Fix choice for completed work.

Diff needs exact labels and a comparison example before more screenshots. Its Compare sheet offers **All changes**, **Working changes**, and **Branch changes**; the guide currently emphasizes internal categories such as “cumulative.” The server resolves a configured or fallback base and uses the common ancestor for branch comparisons, so assuming the latest `main` commit would be wrong. Add a small branch illustration and explain committed versus working changes with the greeting example. Test the explanation against one committed change and one uncommitted edit, including the case where filtering hides an expected file.

End-of-task guidance should distinguish interruption, review, closing a session, and removing its workspace. The close flow already offers **Also delete the worktree** as an unchecked option, with conditions that can disable deletion. Explain this existing control instead of proposing unspecified cleanup. Link a finish-task checklist from Smart Review: inspect changes, run checks, follow the repository’s commit or pull-request requirements, then choose whether to close and retain the worktree. Validate retained and deleted outcomes in a disposable project. Do not describe closing as merging, committing, or automatically accepting the result.

Troubleshooting should become concrete without inventing convenient UI. My earlier request to show where version information lives remains unfinished: the Settings component shows connection controls and warnings, but does not establish a general version field. Trace and walk through a supported diagnostic route before adding instructions to feedback or troubleshooting. Prioritize connection prerequisites and failed message delivery over an exhaustive troubleshooting catalog. For each entry, require a symptom, exact control or command, expected observation, and next action. If only an operator can perform the check, say that before the step.

The design references remain useful, with limits. A [developer discussion](https://www.reddit.com/r/reactjs/comments/1dov15v/) praises Stripe and Tailwind, but cannot establish a ranking of the best-looking sites. [Stripe](https://docs.stripe.com/get-started) offers strong task hierarchy and discoverable Markdown actions; [Linear](https://linear.app/docs) offers consistent cards and spacing. Apply those patterns to Firehose’s actual starting boundary: three compact destinations for connecting, starting a session, and reviewing changes, with connection requirements beside the primary action. Add a quiet article Markdown link using the exports already implemented. Neither recommendation requires another service or a larger dependency stack.

[Tailwind](https://tailwindcss.com/docs/styling-with-utility-classes) connects examples to visible outcomes; Firehose should pair a prompt with an actual result and selected controls. Prioritize the enabled autonomy checkbox, triage followed by Act, and Diff’s Compare sheet because each resolves a confirmed decision gap. Capture desktop and mobile states without implying their layouts match. Keep written instructions complete and use captions explaining the highlighted decision. [Vercel](https://vercel.com/docs) supports the earlier homepage recommendation: a clear starting area and useful alternatives. Remove the homepage’s redundant contents column, while retaining article navigation for longer procedures.

Typography recommendations should acknowledge the existing CSS: body text is already approximately 17 pixels, with 1.8 line height and a 48rem content width. My proposed 17–18 pixel target therefore describes little change. Instead, compare current rendering against modestly tighter paragraph and heading spacing at desktop and phone widths. Preserve code scrolling, keyboard focus, contrast, and both themes. Introduce consistent prerequisites, steps, expected-result, and recovery sections using Markdown first. Add custom components only where repeated content demonstrates a need; attractive consistency should not make agent-readable source harder to maintain.

For review, turn each recommendation into a small issue naming the affected page, source evidence, proposed example, and completion check. Start with the launch paragraph in `getting-started/first-session.md` and the missing dispatch sequence in `tools/smart-review.md`; both affect actions a reader can take immediately. Keep visual revisions separate enough to compare before and after screenshots. A reviewer should be able to reject an unsupported product claim independently of approving better spacing, and verify each change without reconstructing this investigation from memory or private conversations.

Implement three bounded passes. First, revise onboarding, permissions, Smart Review, and Diff against this audit; completion means every consequential choice has its effect and a checkable outcome. Second, prototype homepage hierarchy, spacing, Markdown discovery, and verified captures; run build, link, accessibility, and responsive checks. Third, test navigation groupings with newcomers completing connection, launch, Questions submission, and review dispatch without coaching. Record wrong turns and completion before reorganizing stable URLs. Treat installation access, provider approval walkthroughs, lifecycle behavior, and diagnostics as named unresolved work. Keep hosting and licensing deferred, and commit each completed documentation change locally.
